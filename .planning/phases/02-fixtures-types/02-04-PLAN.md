<objective>
Create `lib/data/register.ts` as the server-only tag-to-asset resolution table, and wire D-17's
two-layer register-isolation rule into `npm run verify`.

Purpose: in production the register is the customer's system of record. Validating a tag on a device
would demonstrate a capability production does not have, so the register must be unreachable from any
client bundle — and that has to be *enforced*, not intended. `server-only` is Next's own compiler-level
enforcement and it was reproduced against this repository. It is not enough on its own: its failure is
folded into the generic `next-build` step's exit code, so `verify` cannot tell a register leak from a
typo. This plan adds the independently-owned, fixture-tested check D-17 requires beside it.

Output: one server-only data module, one check script with two invocation modes, its fixture test, two
new `verify` steps, and one exact dependency. Nothing in this phase imports the register: `lib/access/register.ts`
and `POST /api/referrals` are P9.
</objective>

The script has two mutually exclusive modes, selected by a `--bundle <dir>` flag parsed the way `check-structure.mjs` parses `--build-output`:

**Source mode (no flag) — D-17's first half.** Walk every `.ts` and `.tsx` file under `components/` and `lib/client/`. A missing `lib/client/` is "nothing to check", not an error: it does not exist yet and P4 must not have to touch this script when it appears. Treat those files as roots and follow their imports **transitively**, resolving each `import`/`export … from` specifier that is relative (`./`, `../`) or `@/`-aliased (the `@/*` to `./*` mapping from `tsconfig.json`), trying the `.ts`, `.tsx`, `/index.ts` and `/index.tsx` extensions in that order. The defect message names the root file under `components/` or `lib/client/`, the forbidden target, and the import chain between them, so a violation says which chain to cut. Bare package specifiers are ignored; only first-party paths are followed.

**Bundle mode (`--bundle <dir>`) — D-17's second half.** Read every file under the given directory recursively and fail if any contains the literal `__CAPTURE_REGISTER_SENTINEL__`. A missing directory is a named failure, not a skip: if `verify` asks for the bundle scan and there is no build output, the scan proved nothing and must say so with a non-zero exit. Scope the scan to the directory it is given and never to `.next/server/**`, where the sentinel legitimately appears because `register.ts` is server code.
