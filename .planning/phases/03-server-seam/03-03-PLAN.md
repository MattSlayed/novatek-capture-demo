Create `lib/session/cookie.ts`. Import `signingKey` from `./key.ts` (plan 03-01 wrote it: one lazy
resolver, shared with `lib/proposals/derive.ts`, refusing in production when `CAPTURE_SESSION_KEY` is
absent). Do not add a second key resolver here and do not read `CAPTURE_SESSION_KEY` in this file. Import
`createHmac` and `timingSafeEqual`
from `node:crypto`, `SESSION_COOKIE_MAX_AGE_SECONDS` from `lib/limits`, and `NextRequest` **only** as
`import type` — a statement-level `import type`, never an inline `{ type NextRequest }` modifier, because
only the statement form is fully erased by Node's type stripping and the unit test depends on that.

Export:

- `export const SESSION_COOKIE_NAME = "cap_session"` — one definition.
- `mintSession(accountId: string, nowMs?: number): { session: Session; value: string }` — builds the
  `Session` (`sid` from `crypto.randomUUID()`, `account_id`, `issued_at` and `expires_at` as ISO-8601
  UTC with `Z`, the expiry `SESSION_COOKIE_MAX_AGE_SECONDS` after issue) and returns the opaque cookie
  value: the base64url of the compact payload, a `.` separator, then the base64url HMAC-SHA256 of that
  payload under `signingKey()`. Take `nowMs` as an optional last parameter defaulting to `Date.now()`
  purely so the unit test can pin time; comment that it is never supplied by a route and never read from
  a body.
- `readSession(request: NextRequest): SessionResult` where
  `export type SessionResult = { ok: true; session: Session } | { ok: false; reason: "absent" | "malformed" | "bad_signature" | "expired" }`.
  Read the raw value with `request.cookies.get(SESSION_COOKIE_NAME)?.value`. Verify by recomputing the
  HMAC over the payload and comparing with `timingSafeEqual` behind an explicit
  `if (a.length !== b.length) return false` guard — `timingSafeEqual` throws rather than returning
  `false` on mismatched lengths, and that guard is load-bearing, not defensive. Check the signature
  **before** parsing the payload's contents and before the expiry comparison, and comment the ordering:
  an attacker must not learn from the reason code whether a forged payload was well-formed.
- `sessionCookieOptions(value: string)` — returns the attribute object the responder passes straight to
  `response.cookies.set`: `name: SESSION_COOKIE_NAME`, `value`, `httpOnly: true`, `sameSite: "lax"`,
  `maxAge: SESSION_COOKIE_MAX_AGE_SECONDS`, `secure: process.env.NODE_ENV === "production"`,
  `path: "/"`. Never assemble a `Set-Cookie` string here or anywhere.
- `clearedSessionCookieOptions()` — the same object with `value: ""` and `maxAge: 0`.
- `verifySessionValue(value: string): SessionResult` — the same verification against a bare string, so
  the unit test and `/api/sync`'s envelope path can both reach it without a `NextRequest`.

Add one comment stating FR-3's limitation plainly, because the Limits screen and the handover both quote
it later: the credential is stateless, so a copied cookie stays valid until it expires and no revocation
is claimed.

Create `lib/session/cookie.test.mjs`. Set `process.env.CAPTURE_SESSION_KEY` to a fixed test value at the
top of the file so every assertion is deterministic, and comment why. Assert:
- a minted value round-trips: `verifySessionValue(mintSession("acc-mabaso").value)` is `ok` with the
  same `account_id`;
- flipping one character of the signature yields `{ ok: false, reason: "bad_signature" }` and never
  throws — the length-guard path;
- truncating the value to remove the separator yields `malformed`, not a throw;
- a value minted with `nowMs` far enough in the past that `expires_at` has passed yields `expired`;
- a value signed with a different key yields `bad_signature`;
- `readSession` works against a hand-built stub `{ cookies: { get: (n) => n === "cap_session" ? { value } : undefined } }`,
  and returns `{ ok: false, reason: "absent" }` when the stub returns `undefined`;
- `sessionCookieOptions("x")` has `httpOnly: true`, `sameSite: "lax"`, `path: "/"` and
  `maxAge === SESSION_COOKIE_MAX_AGE_SECONDS`, and `clearedSessionCookieOptions().maxAge === 0`;
- the module's source contains no `Set-Cookie` literal — read the file with `node:fs/promises` and

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the cookie value → the server's notion of who is acting | The cookie is the only identity input; a forgeable one makes every downstream control decorative |
| a request body, query parameter or header → an actor field | FR-4 and FR-23's negative sets exist because this is the boundary an attacker will push on |
| an id in a URL → the record behind it | The order id is attacker-chosen; ownership must be decided before existence or the difference maps the fixture set |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-11 | Spoofing | forged `cap_session` cookie | mitigate | Task 1 signs the payload with HMAC-SHA256 under plan 03-01's lazily-resolved `signingKey()` and verifies the signature before parsing the payload or comparing the expiry; the unit test proves a one-character signature change and a foreign-key signature both return `bad_signature`. |
| T-3-12 | Information Disclosure | timing side channel on the session signature (CWE-208) | mitigate | Task 1 compares only with `timingSafeEqual` behind an explicit length guard, never `===` or `Buffer.equals`; acceptance criteria grep for the forbidden forms. |
| T-3-13 | Spoofing | an actor field taken from the request body | mitigate | Task 2's `deriveAccount` accepts exactly one parameter, a `SessionResult`, so no body value can reach it; the module's source is asserted to contain no `body`, `request`, `headers` or `searchParams`, and plan 03-12's `check-actor-field.mjs` asserts no other module assigns an actor field. |
| T-3-14 | Information Disclosure | IDOR — distinguishing another account's order from a nonexistent one | mitigate | Task 3's `orderOwned` returns before touching `ORDER_BY_ID` when the id is not in the account's set, so both cases take one path; the unit test asserts both return `null`, and the route suite proves byte-identity over HTTP. |
| T-3-15 | Elevation of Privilege | an authorisation decision made from `rbac_tier` rather than order assignment | mitigate | Tasks 2 and 3 both forbid the identifier in source and assert its absence; Phase 2 D-20's JSDoc already marks the field display-only, and FR-57's non-bypassability document in plan 03-15 names `lib/access/scope.ts` as the only decision site. |
</threat_model>
