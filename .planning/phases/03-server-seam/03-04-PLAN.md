<objective>
Build the two authored modules: the match a verify-purpose capture returns, and the proposals that come
with it, each declared over the asset record and the fixture snapshot and nothing else.

Purpose: AD-8 is the architectural claim this preview makes about itself — no model ran, and the proof
is that the capture payload is not reachable from the code that produces the answer. A build rule in
plan 03-06 asserts it; this plan is what makes the assertion true. AD-5 makes a proposal's identity
derived rather than stored, which is what turns FR-27's byte-identity into a structural consequence
instead of a second code path.

Output: two modules with two unit tests, no route, no store access, no capture payload anywhere in
either signature.
</objective>

Create `lib/proposals/derive.ts`. It carries two separate concerns and the header comment must say so:
the authored content (AD-8, declared over `(assetId, fixtureSet)`) and the derived identity (AD-5, an
HMAC over three ids). Keep them as separate exported functions; never fold the id derivation into the
content function, because the content function's parameter list is the thing plan 03-12's build rule
asserts.

Export:

- `export type AuthoredProposal = Omit<Proposal, "id" | "capture_id" | "order_id" | "issued_at" | "state">` —
  `observation_id` comes through from `Proposal` itself, which plan 03-01 gave that field for AD-5, so
  this type does not restate it
- `export function authoredProposals(assetId: string, fixtureSet: string): AuthoredProposal[]` —
  exactly two parameters, named exactly `assetId` and `fixtureSet`. Returns one entry per
  `OBSERVATIONS_BY_ASSET.get(assetId)` row when `fixtureSet === FIXTURE_VERSION`, and an empty array
  when the asset has no key in that map or the fixture set does not match. Each entry carries
  `observation_id` (the row's own `id`), `asset_id`, `observation` (the row's `wording`, copied, never
  reworded) and `provenance`.
- `export function deriveProposalId(accountId: string, clientId: string, observationId: string): string`
  — exactly RESEARCH.md §Pattern 3: `createHmac("sha256", signingKey())` over `accountId`, `clientId`
  and `observationId` joined by NUL bytes, returned as `.digest("base64url")`. One bare digest. No
  payload half, no `.` join, nothing encoded into the id that could be read back out of it.
- `export function proposalIdMatches(candidate: string, accountId: string, clientId: string, observationId: string): boolean`
  — takes all three derivation inputs from its caller, re-derives, and compares with `timingSafeEqual`
  behind an explicit length guard, returning `false` on a length mismatch rather than letting
  `timingSafeEqual` throw. It never inspects the candidate for structure, because a digest has none. A
  malformed candidate returns `false` by the same path a valid-but-foreign one does.

Do not write a `parseProposalId`, and do not encode the client id or the observation id into the id in
any form. AD-5 is explicit about where the inputs come from: the decision item carries exactly two
identity fields — `capture_client_id` and `observation_id` — and the triple is reconstructed from those
two plus the session's account. That is the whole of how statelessness is achieved, and the
four-parameter signature is what enforces it: an instance that never issued the proposal has every input
in the request, reads nothing from the store, re-derives, matches and records the decision — exactly as
EXPERIENCE.md requires and with no "server restarted" message anywhere. Write that reasoning in a
comment. Comment the NUL separators too: account ids and client ids are controlled formats here, so a
plain separator would be safe in practice, but a NUL byte is unambiguous and costs nothing.

Compose `provenance` as follows, and write each step's reason in a comment:
- resolve the row's `drawn_from` first against `DEVIATION_BY_ID`, then against the `facts` array of

- take that record's own `provenance` and carry `source_uri`, `source_version`, `extracted_at`,
  `source_label` and `system_of_record` through unchanged — the proposal card names the record the
  observation was drawn from, and that name comes from the record, not from here.
- set `confidence: null` and `extractor: "authored"`.
- set `grade` from the **observation's** own `grade` field, not the cited record's. Comment why: an
  authored observation is an inference the record supports or a context it situates, never an
  extraction, so its grade is one of `INFERRED`/`AMBIGUOUS` and the cited record's own grade describes
  the record rather than the inference drawn from it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the capture payload → the authored answer | AD-8's whole claim is that the bytes never reach the answer; a parameter is all it would take to make the claim false |
| a client-supplied proposal id → a decision | The id is attacker-chosen; if it is looked up rather than re-derived, a guess becomes a decision |
| one account's proposal → another account's decision | The account is one of the three HMAC inputs, so cross-account reuse fails at the same step a fabrication does |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-17 | Spoofing | a client constructing a valid proposal id | mitigate | Task 2 derives every id as a bare HMAC-SHA256 digest under `signingKey()` over account, client id and observation id; no id is ever minted sequentially or stored-and-echoed, the unit test asserts two ids from consecutive observation ids share no long prefix, and a further test asserts the decoded digest contains neither input — a client holding an id learns nothing from it that it did not already send. |
| T-3-18 | Information Disclosure | distinguishing an unknown proposal from another account's proposal | mitigate | Task 2's `proposalIdMatches` fails identically for a fabricated candidate and for a valid id under a different account, before any state is read; the unit test names that case as REQ-FR-27's unit half and the route suite proves the byte-identity over HTTP. |
| T-3-19 | Information Disclosure | timing side channel on the derived id comparison | mitigate | `timingSafeEqual` behind an explicit length guard, never `===` or `Buffer.equals`; an acceptance criterion greps for the guard and the unit test asserts no throw on a length mismatch. |
| T-3-20 | Tampering | the capture payload influencing the verification result or the proposal set | mitigate | Both authored functions take exactly `(assetId, fixtureSet)`; both unit tests assert the parameter count and names by source inspection, and both assert the source contains no capture-payload identifier. Plan 03-06's `check-fixture-inputs.mjs` re-asserts it at build time over the import graph. |
| T-3-21 | Repudiation | a proposal citing a record that does not exist, so the decision cannot be re-checked | mitigate | Task 2 throws `UnknownCitedRecordError` rather than falling back when `drawn_from` resolves to neither a deviation nor one of the asset's facts; `scripts/check-observations.mjs` already proves the shipped fixtures resolve. |
</threat_model>
