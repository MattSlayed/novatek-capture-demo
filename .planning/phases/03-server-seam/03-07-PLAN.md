Export `GET` and `HEAD`. Both call `await connection()` from `next/server` as their **literal first

`GET` returns, through `ok()`, `{ ok: true, store: "memory", boot_id: BOOT_ID, uptime_s: uptimeSeconds(),

would corrupt D-07's floor. Say so in a comment.

Export no `runtime` and no `dynamic` from this file or any other in this plan.

Create `app/api/session/route.ts` exporting `POST`, `GET` and `DELETE`.

`POST`: parse the body inside a try/catch, returning `fail("bad_request")` on a parse failure. Take
`persona_id` and nothing else — run the body through `pick` against `ACCEPTED_BODY_FIELDS.session` so
any other field is dropped at parse and appears nowhere, including in the response. Resolve `persona_id`
through `ARTISAN_BY_ID`; an unknown one returns `fail("unknown_persona")`, which is a 404 with a stated
reason. Mint the session with `mintSession(persona_id)`, build the success response with `ok({ account,
session }, { status: 201, headers: { "X-CAP-Account": account.id } })`, and attach the cookie with
`setCookie(response, sessionCookieOptions(value))`. Return exactly the `Artisan` record and the `Session`
record — no field of the body is echoed and none is persisted (FR-1).

`GET`: `readSession(request)` then `deriveAccount`. `null` → `fail("no_session")` (401). Otherwise
`noteContact(account)` and `ok({ account: account.artisan }, { headers: { "X-CAP-Account":
account.account_id } })`.

`DELETE`: clear the cookie unconditionally — build a 204 through `ok(null, { status: 204 })` and attach
`setCookie(response, clearedSessionCookieOptions())`. Add a comment carrying FR-3's stated limitation in
the same words `lib/session/cookie.ts` uses: the credential is stateless, so a copied cookie stays valid
until it expires and no revocation is claimed. Do not close any clock segment here — D-08 says a running
segment survives the end of a session and ends only when an explicit `order_close` arrives from the same
account; state that in a comment so no one later "tidies" it.

Read the cookie with `request.cookies.get(...)` inside each handler, never in middleware and never from
a module-level helper that takes something other than the request. No `proxy.ts` and no `middleware.ts`
is created by this plan or any plan in this phase.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the request → the identity the server acts as | The cookie is the only reader; a query parameter, a body field or a header naming an account must have no reader at all |
| an order id in the URL → the record behind it | FR-6's byte-identity begins here, at the first route that takes an id |
| the build → `/api/health`'s answer | A route with no dynamic API is prerenderable, and a frozen `boot_id` would make curl H pass while proving nothing |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-32 | Spoofing | an `account` query parameter, `account` body field or `X-Account` header shaping the order list | mitigate | Task 2's handler reads neither `searchParams` nor any request header other than the cookie, and takes no body; the acceptance criteria grep for the absence of every reader, so the negative set fails for lack of a code path rather than by a guard. |
| T-3-33 | Information Disclosure | `observation_ids` leaking to a client through the order detail | mitigate | Task 2 builds a new asset object per entry with the field omitted, never deleting a key from the shared fixture record; the acceptance criteria grep for the absence of `delete `. |
| T-3-34 | Information Disclosure | a cache-frozen `/api/health` answer presenting a stale instance as live | mitigate | Task 1 calls `await connection()` as the literal first statement of both handlers and an acceptance criterion requires the build output to mark the route dynamic rather than static. |
| T-3-35 | Spoofing | a session cookie readable by page JavaScript or sent over plaintext | mitigate | The cookie options come from `sessionCookieOptions` (`HttpOnly`, `SameSite=Lax`, `Secure` under production, bounded `Max-Age`); this plan attaches them through the responder and names no attribute of its own. |
| T-3-36 | Information Disclosure | a success-only counter appearing on a not-found response | mitigate | Task 2 reaches not-found only through `notFound()`, which takes no parameters; `fail` throws on a success-only header; the route suite's comparator in plan 03-13 proves it over the wire. |
</threat_model>
