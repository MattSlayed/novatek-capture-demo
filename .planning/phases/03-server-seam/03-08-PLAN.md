<objective>
Ship the clock: open, close and the read-only hours route, each a thin handler over the one writer.

Purpose: the clock is the requirement with the most ways to go quietly wrong — a second segment on a
repeat open, a lost prior segment on a reopen, a hand-written 405 that carries none of the universal
headers. All three are prevented here by making the route do nothing except turn a request into a
`SyncItem` and hand it to `applyItem`.

Output: three route files, zero new library logic, one explicit `POST` handler whose whole body is a
refusal.
</objective>

  <action>
Create both route files. They are near-identical; write them as two files rather than one shared helper,
because a shared helper between two route files is a second place to look when one of them misbehaves —
but keep the bodies short enough that the duplication is obvious rather than hidden.

Each exports `POST(request, context: { params: Promise<{ id: string }> })` and nothing else. No
`runtime`, no `dynamic`.

Sequence, each step returning immediately:
1. `const { id } = await context.params`.
2. `readSession(request)` then `deriveAccount`; `null` → `fail("no_session")`.
3. `noteContact(account)`.
4. `orderOwned(account, id)` → `null` → `notFound()`. Do this before parsing the body: ownership before
   anything else the request carries, so a malformed body on an unowned order is still a not-found and
   never a `bad_request` that would distinguish it.
5. Parse the body in a try/catch; a parse failure → `fail("bad_request")`. Run the parsed object through
   `pick(body, ACCEPTED_BODY_FIELDS.orders_open)` (or `orders_close`) so only `client_id` survives.
6. Build the `SyncItem` **on the server**: `client_id` from the picked body, `kind` `"order_open"` or
   `"order_close"`, `schema_version` from `SYNC_ITEM_SCHEMA_VERSIONS[kind][0]`, `order_id: id`,
   `created_at` the server's own ISO-8601 UTC `Z` now, `attempts: 1`, `state` the online-path marker
   that makes `applyItem` derive `arrived_via: "immediate"`, `claimed_account_id: account.account_id`
   and an empty payload object. Comment that every field here is server-derived or enumerated, so the
   online path and the sync path hand `applyItem` the same shape and there is no second writer.
7. `await applyItem(sessionResult, item)`.
8. Dispatch the outcome. `result.status === "recorded"` or `"duplicate"` → `ok({ clock:
   result.server.clock }, { headers: { "X-CAP-Clock": <the segment count>, "X-CAP-Account":
   account.account_id } })` with status 200. Comment the `duplicate` branch against D-06 and FR-7: a
   second open of a running order is a `200 { clock }` with no new segment, not an error, and
   `already_open` is not introduced by this phase. Anything else → `fail(outcome.code, result.detail)`,
   which maps `not_open` and `order_closed` to 409 through `STATUS_BY_CODE`.

Never call `NextResponse.json` and never construct a `Response`. Never write a refusal sentence as a
literal — `result.detail` already carries the one from `lib/copy/conflicts.ts`.
  </action>

`GET`: read the cookie in the handler, derive the account, `fail("no_session")` when there is none, then
`noteContact(account)`. Return `ok({ clocks })` where `clocks` is `readClocksForAccount(account.account_id)`

and the `elapsed_s` the server computed from the segments it stamped. Withhold nothing: FR-58's
read-back is the reason this route exists, and a filtered view here would be the one dishonest thing it
could do. Say so in a comment, and record D-08 beside it: a segment opened under an earlier session is
still here and still accruing, because the clock is keyed by order and account rather than by session id.

Compute nothing from a request value. The handler takes no query parameter and no body; state in a
comment that FR-10's "no write route accepts an artisan-supplied duration or hour value" is true here
for lack of any reader, and that the enumerations in `lib/reconcile/validate.ts` carry no `elapsed_s`,
`hours` or `duration_s` for the same reason.

`POST`: the whole handler body is `return fail("method_not_allowed")`. Write the reason above it from
the empirical finding: Next generates its own 405 before the request reaches application code, and that
405 carries none of the universal headers and a plain-text body, so relying on it would satisfy curl
check G's status code while violating NFR-F1. Do not read the session here — HTTP method negotiation
precedes identity, nothing in the requirements exercises an authenticated `POST /api/hours`, and a
session check would make the refusal differ between a signed-in and a signed-out caller for no gain.
State that choice and its reason in the comment rather than leaving it implicit.

Do not call `connection()` in either handler: `GET` reads the cookie, which is a Dynamic API and is
sufficient on its own; `POST` is never build-time cacheable.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a request body → the accrued record | The clock is the record that could become pay; any body field that could influence it is the boundary |
| the framework's own routing layer → the response contract | Next answers 405 before application code runs, outside every guarantee `lib/http/respond.ts` makes |
| an order id in the URL → a clock segment | Ownership must be settled before the body is read, or a malformed body on an unowned order answers differently from one on a fabricated order |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-37 | Tampering | an artisan-supplied duration or hour value reaching the accrued record | mitigate | Task 1 picks the open and close bodies down to `client_id` alone and builds every other `SyncItem` field on the server; Task 2's `GET` reads no query parameter and no body; plan 03-12's `check-accepted-fields.mjs` re-asserts both enumerations at build time (REQ-FR-10). |
| T-3-38 | Information Disclosure | a route auto-answering 405 without the universal headers | mitigate | Task 2 exports an explicit `POST` whose whole body is `fail("method_not_allowed")`, so the refusal carries `Cache-Control: no-store`, `X-CAP-Store`, `X-CAP-Instance` and the `{ error, detail }` envelope like every other response (REQ-NFR-F1). |
| T-3-39 | Information Disclosure | a malformed body on an unowned order answering differently from one on a fabricated order | mitigate | Task 1 calls `orderOwned` before the body parse and returns `notFound()` from a single call site; the acceptance criteria assert the ordering by line position. |
| T-3-40 | Tampering | a second clock segment created by a repeat open, inflating the accrued record | mitigate | The route never touches the store; `applyItem` returns `duplicate` with the unchanged clock and the route renders it as a plain 200, proved at the unit level in plan 03-05 and over HTTP in plan 03-13 (REQ-FR-7, D-06). |
</threat_model>
