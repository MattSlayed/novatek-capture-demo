<objective>
Ship the three capture-and-decision routes: the verify-purpose capture that returns the authored match
and its proposals, the evidence capture that returns neither, and the decision that accepts or rejects
one proposal.

Purpose: these are curl checks B, C and D and the whole of FR-23's and FR-27's negative sets. They are
also where AD-20 stops being a principle: the accepted-field enumeration is applied here, at parse, and
a forged actor field ceases to exist before any code could read it.

Output: three route files. The authored modules are never called from a route — only the writer reaches
them.
</objective>

Create both files. Each exports `POST` only. No `runtime`, no `dynamic`.

Shared sequence, each step returning immediately:
1. `readSession(request)` then `deriveAccount`; `null` → `fail("no_session")`.
2. `noteContact(account)`.
3. Parse the body in a try/catch; a parse failure → `fail("bad_request")`.
4. `pick(body, ACCEPTED_BODY_FIELDS.verify)` — or `.captures` — so exactly
   `client_id, order_id, asset_id, kind, purpose, captured_at, sha256, bytes, mime, duration_ms, thumb`
   survive and every other key, `captured_by` and `account_id` included, is gone before the next line
   runs. Comment that this is AD-20 at the only place it can be structural: the field is dropped at
   parse, so nothing downstream can read it and nothing can echo it.
5. `orderOwned(account, picked.order_id)` → `null` → `notFound()`. Ownership before shape, as AD-1's
   order requires, so a malformed body on an unowned order is still a not-found.
6. Build the `SyncItem` on the server: `client_id` from the picked body, `kind: "capture"`,
   `schema_version` from `SYNC_ITEM_SCHEMA_VERSIONS.capture[0]`, `order_id` from the picked body,
   `created_at` the server's own ISO-8601 UTC `Z` now, `attempts: 1`, the immediate-path `state`,
   `claimed_account_id: account.account_id`, and a payload picked with
   `ACCEPTED_PAYLOAD_FIELDS.capture`. Force `purpose` to `"verify"` in the verify route and to
   `"evidence"` in the captures route rather than trusting the body's value — the route is the purpose,
   and a body that disagrees with the URL it was sent to does not get to decide which one wins. Comment
   that.
7. `await applyItem(sessionResult, item)`.
8. Dispatch: `recorded` → `ok(...)` with status 201; anything else → `fail(outcome.code, result.detail)`,
   which maps `asset_not_in_order` and `order_closed` to 409, `media_too_large` to 413 and `bad_shape`
   to 422 through `STATUS_BY_CODE`.

The verify route's success body is `{ capture, verification, proposals }` from `result.server`, with
headers `X-CAP-Verification: "authored"`, `X-CAP-Proposals` set to the proposal count and
`X-CAP-Account`. The `"authored"` value is the header's own literal, not a governed sentence — say so in
a comment, and note that the sentence itself resolves through `GOVERNED.authoredVerification` at render
time in P5 and is never written here.

The captures route's success body is `{ capture }` alone, with headers `X-CAP-Capture` set to the
capture id and `X-CAP-Account`. It stamps neither `X-CAP-Verification` nor `X-CAP-Proposals` — an
evidence capture produces no verification and no proposals, and a header claiming otherwise would be the
kind of quiet overclaim this project exists to avoid.

Neither route imports `lib/verify/authored.ts` or `lib/proposals/derive.ts`. Say so in a comment with
the reason: the writer reaches them, the route does not, so there is exactly one path from a request to
an authored answer. Plan 03-06's `check-fixture-inputs.mjs` walks the graph in the other direction; this
is the near side of the same rule.

Catch `UnknownCitedRecordError` at the route boundary with an `instanceof` guard and rethrow anything
else, following the sibling's shape. Map it to `fail("bad_shape", ...)`? No — it is a fixture defect,
not a client defect. Let it propagate as an unhandled error so the build's own logs carry it, and write
that choice and its reason in a comment: a fixture that cites a record it does not hold is a repository
bug, and dressing it as a client refusal would hide it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a request body → an actor field on a record | The one boundary FR-23's negative set exists to push on, and the only place it can be closed structurally is the parse |
| a proposal id chosen by a client → a decision | Re-derivation under the acting account is what collapses "unknown" and "not yours" into one event |
| the capture payload → the authored answer | A route that imported the authored modules would be a second path from a request to an answer |
| a declared media size → the store | An oversized declaration must be refused before anything is written, not after |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-41 | Spoofing | a body naming a different artisan (`decided_by`, `captured_by`, `account_id`) | mitigate | Both tasks run every body through `pick` against its route's enumeration before any other line; the field ceases to exist rather than being ignored, and the writer assigns the actor field only from the attribution function (REQ-FR-23). |
| T-3-42 | Information Disclosure | distinguishing an unknown proposal from another account's proposal | mitigate | Task 2 reaches the refusal only through `notFoundProposal()`, which takes no parameters and has one call site; the writer decides it by re-derivation at the ownership position, before any state read (REQ-FR-27). |
| T-3-43 | Tampering | the capture payload influencing the authored match or the proposal set | mitigate | Neither route imports `lib/verify/authored.ts` or `lib/proposals/derive.ts`; the acceptance criteria grep for the absence, and plan 03-06's `check-fixture-inputs.mjs` walks the import graph from the other side (REQ-FR-17). |
| T-3-44 | Denial of Service | an oversized thumbnail or declared byte count reaching the store | mitigate | The writer's validator refuses `media_too_large` against `lib/limits`' ceilings before the write path; the route maps it to 413 with the sentence the artisan can act on (REQ-FR-19). |
| T-3-45 | Elevation of Privilege | a capture bound to an asset outside the artisan's order | mitigate | `orderOwned` runs before the item is built and `assetInOrder` runs inside the writer, refusing `asset_not_in_order` with its own sentence; a referral is a different object and is not reachable from this refusal (REQ-FR-18). |
</threat_model>
