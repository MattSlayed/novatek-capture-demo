  <action>
Create `app/api/sync/route.ts` exporting `POST` only. No `runtime`, no `dynamic`.

Write the header comment first, because it is the part a later reader most needs: this route returns
HTTP 200 whenever the envelope itself parsed, and every per-item outcome — recorded, duplicate, conflict
or rejected alike — is carried in `results[]` rather than in the status line. A batch is not a
transaction and a refused item does not fail its neighbours.

Sequence, before any item is touched:
1. `readSession(request)` then `deriveAccount`; `null` → `fail("no_session")` (401). The envelope-level
   session check lives here rather than per item: the seed's route table gives this route a 401, and a
   per-item `no_session` would be a second rendering of one fact.
2. `noteContact(account)`.
3. Parse the body in a try/catch; a parse failure → `fail("bad_request")` (400).
4. Measure the encoded size **before** parsing further: take the raw text with `await request.text()`
   and `JSON.parse` it yourself rather than `await request.json()`, so the byte length is available
   without re-serialising. Use `Buffer.byteLength(raw, "utf8")`. Comment why the raw text is measured
   rather than the parsed object: the ceiling is about what crossed the wire, and re-serialising a
   parsed object measures something else.
5. `pick(body, ACCEPTED_BODY_FIELDS.sync)` so only `items` survives. A missing or non-array `items` →
   `fail("bad_request")`.
6. The ceiling, before the loop: `items.length > SYNC_MAX_ITEMS` or the measured byte length
   `> SYNC_MAX_ENCODED_BYTES` → `fail("batch_too_large")` (413), carrying
   `TRANSPORT_COPY.batch_too_large.sentence` through `detailFor`. Comment that this app-level 413 is a
   different refusal from `lib/copy/governed.ts`'s `PLATFORM_413`, which is the hosting platform
   refusing before the preview server saw the body at all, and that neither sentence is used in place of
   the other.
7. Refuse nothing else at the envelope level. An item whose shape is wrong is one item's problem.
  </action>

  without calling the writer only when the item has no usable `client_id` — otherwise pass it to
  `applyItem` anyway, so the attempt is retained (AD-1). Comment the one exception: an item with no
  UUID-shaped `client_id` cannot be keyed for idempotency or named in a result, so it is refused
  `bad_shape` at the envelope and the attempt is written with a `null` client id.

  `outcome.code` — the transport status belongs to the envelope, not to the item.

  writer mutates shared module state, so they are applied one at a time in arrival order. Say so in a
  comment.

behaviour and until then the refusal is honest rather than a silent drop. Write that in a comment; do
not special-case the kind in this file.

`X-CAP-Sync-Recorded`, `X-CAP-Sync-Duplicate`, `X-CAP-Sync-Conflict`, `X-CAP-Sync-Rejected`, each the
count of results with that status, plus `X-CAP-Account`. Stamp them once, after the loop — never
per item, and never by mutating a response mid-loop.

Return `ok({ server_time, results }, { status: 200, headers: { ...the five } })` where `server_time` is
the server's own ISO-8601 UTC `Z` now. Status 200 whenever the envelope parsed, including a batch in

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a batch envelope → server memory | The batch is the largest thing a client can send; the ceiling is the only thing between it and the store |
| a queued item → the record | An item may have been composed hours earlier on a device whose clock and whose acting account may both have moved |
| the sync path → the online path | A second writer on this path would make every guarantee the online routes hold conditional on which door the request used |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-46 | Denial of Service | an oversized batch by item count or by bytes | mitigate | Task 1 measures the raw request text with `Buffer.byteLength` and refuses `413 batch_too_large` against `SYNC_MAX_ITEMS` and `SYNC_MAX_ENCODED_BYTES` before the loop starts, carrying the app-level sentence rather than the platform one (D-02, REQ-FR-19). |
| T-3-47 | Tampering | a sync-only write path bypassing the check order | mitigate | Task 2 has exactly one `applyItem` call site and no store import; plan 03-12's `check-single-writer.mjs` asserts over the import graph that no file under `app/api` reaches the store's mutating exports (REQ-FR-24). |
| T-3-48 | Spoofing | an item carrying another account's `claimed_account_id` | mitigate | The writer compares the field against the acting account and returns `account_mismatch`; the field is never copied onto a record, per `types.ts`'s own note that it is compared and never trusted. |
| T-3-49 | Information Disclosure | an unowned order id in a batch item answering differently from a fabricated one | mitigate | Every item goes through the same `applyItem` as the online routes, which decides ownership before state; the route adds no branch of its own, and the route suite's comparator in plan 03-13 proves the per-item results are byte-identical (REQ-FR-6). |
| T-3-50 | Repudiation | an item silently dropped from a batch | mitigate | The loop never breaks and never uses `Promise.all`; every item produces a `SyncItemResult` and the four counters are tallied from `results` rather than from a separate tally, so a dropped item would change the counters and be visible (D-01). |
</threat_model>
