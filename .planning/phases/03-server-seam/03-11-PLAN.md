Create `lib/walk/payload.ts`. One exported function:

  `export function buildWalkPayload(account: ActingAccount, order: WorkOrder, nowMs?: number): WalkPayload`

`nowMs` is optional and defaults to `Date.now()`, purely so the unit test can pin `issued_at`; comment
that no route supplies it. Follow the sibling's `buildManifest` shape: one function, local arrays,
per-entry loops, one big typed return at the end. Do not split it into exported helpers.

Populate every field D-03 names:
- `schema: "novatek.capture.walk/1"` and `issued_at` as ISO-8601 UTC `Z`.
- `store: { kind: "memory", instance: BOOT_ID, ttl_s: STORE_TTL_SECONDS, statement }` where `statement`
  is `GOVERNED.memoryStore.before + GOVERNED.memoryStore.strong + GOVERNED.memoryStore.after`.
  Assemble it from the triple — never write the sentence as a literal, not even in a comment, because
  `check-governed.mjs` sweeps comments too.
- `account: account.account_id`.
- `order` — the `WorkOrder` record as the fixture holds it.
- `clock` — `readClock(account.account_id, order.id)`, or a zero-segment clock shape when none exists.
- `assets[]` — one entry per `assetsForOrder(order)`, each carrying:
  - `asset_id` and `tag` from the asset record; `observation_ids` is **not** carried through, because it
    is server-only (`lib/data/types.ts` says so) and this payload is the record handed onward;
  - `verification` — the stored `VerificationResult` for the most recent verify-purpose capture on that
    asset, or the honest empty state when there is none. Decide which and say why in a comment; do not
    invent a verification that never ran;
  - `captures[]` — every stored capture for that asset in this order, each extended with
    `thumb_present` (a boolean derived from whether `thumb` is a non-empty string) and
    `audio_left_device: false` as a literal `false`. Carry `thumb` itself through unchanged. Comment
    that `audio_left_device` is a constant because no route in this preview accepts audio bytes, and
    that the field exists so the record states it rather than leaving it to be inferred;
  - `candidate_facts[]` — every proposal for that asset whose state is `accepted`, each extended with
    `accepted_by` and `accepted_at` from the decision that accepted it and `arrived_via` from that same
    decision. Comment that all three are read off the server's own decision record, never off any claim
    the client made (FR-54);
  - `rejected[]` — every proposal for that asset whose state is `rejected`, retained with its decision;
  - `open[]` — every proposal for that asset whose state is `open`.
  The three sets are disjoint and are built by filtering on `state`, so a proposal appears in exactly
  one. Say so in a comment and name FR-53: a referral is never presented as an accepted observation, and
  the same discipline keeps a rejection from being presented as an open proposal.
- `referrals: []` — a literal empty array with a comment saying P9 supplies both the route and the
  entries, and that an empty array is the honest present state rather than a placeholder.
- `redaction: { ran: false, statement }` where `statement` is assembled from `GOVERNED.noRedaction`'s
  triple the same way.

Import only read-only accessors from `lib/store/memory.ts`. Import nothing from `lib/reconcile`,
nothing from `app/`, and never `lib/data/register.ts`. Say so in the header: this module reads and
assembles; it writes nothing, which is what keeps `check-single-writer` green with it in the graph.

Create `lib/walk/payload.test.mjs`. Build state by calling `applyItem` rather than by writing to the
store directly, so the test exercises the real path. Assert:
- every top-level key of `WalkPayload` is present on a freshly built payload for an order with nothing
  recorded, and `assets` has one entry per `order.asset_ids` member;
- `store.instance` equals `BOOT_ID` and `store.ttl_s` equals `STORE_TTL_SECONDS`;
- `store.statement` and `redaction.statement` are both non-empty and each equals the concatenation of
  its `GOVERNED` triple — compare against the triple, never against a literal;
- `redaction.ran` is `false` and every capture's `audio_left_device` is `false`;
- `referrals` is an empty array;
- after an accept, the proposal appears in `candidate_facts` with `accepted_by` equal to the acting
  account, a non-null `accepted_at` and an `arrived_via` matching the decision, and appears in neither
  `rejected` nor `open`;
- after a reject, the proposal appears in `rejected` and in neither of the other two, and it is still
  there after a second unrelated write — nothing deletes a rejection (FR-25, curl E);
- `thumb_present` is `true` for a capture that carried a thumbnail and `false` for one that did not;
- no asset entry carries an `observation_ids` key.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an order id in the URL → the whole record for that order | The walk payload is the largest disclosure in the system; ownership must gate it exactly as it gates the order detail |
| the store and the fixtures → the record handed onward | Anything the assembler infers rather than reads becomes an unsupported claim in the artefact a reviewer will read most closely |
| a governed sentence → the payload | A literal copy inside the payload would be a second definition of a sentence the whole project defines once |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-3-51 | Information Disclosure | another artisan's whole order record retrieved by guessing an id | mitigate | Task 2 calls `orderOwned` before the assembler and reaches not-found only through `notFound()`, which takes no parameters; the route suite's comparator proves an unowned id and a fabricated id are byte-identical (REQ-FR-6, REQ-FR-52). |
| T-3-52 | Information Disclosure | the server-only `observation_ids` field reaching the record handed onward | mitigate | Task 1 builds each asset entry as a new object carrying only the `WalkPayload` fields; an acceptance criterion asserts no asset entry carries the key. |
| T-3-53 | Repudiation | a rejection disappearing from the record | mitigate | Task 1 filters the three proposal sets on `state` so they are disjoint by construction, and the unit test asserts a rejection is still present after a later unrelated write (REQ-FR-25, curl E). |
| T-3-54 | Tampering | a header claiming a fact count the body does not carry | mitigate | Task 2 derives `X-CAP-Walk-Facts` from the payload the assembler returned rather than re-querying the store, so the two cannot disagree. |
| T-3-55 | Spoofing | a client's claim about how a decision arrived being presented as the server's fact | mitigate | Task 1 reads `accepted_by`, `accepted_at` and `arrived_via` off the server's own decision record and never off the client's claim, with the reason in a comment (REQ-FR-54). |
</threat_model>
