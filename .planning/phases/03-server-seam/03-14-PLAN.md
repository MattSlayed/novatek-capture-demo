Requirements of the script itself:
- `#!/usr/bin/env bash` and `set -u` (not `set -e` — a failing check must print `FAIL` and let the
  remaining checks run, because a reviewer wants the whole picture, not the first stumble). Say that in
  a comment.
- `B="${B:?set B to the base URL, e.g. B=https://example.vercel.app}"` as the first executable line, so
  running it with no base URL prints a usable message rather than a stream of connection errors.
- Two cookie jars in a temporary directory, cleaned up with a `trap`: one for `acc-mabaso` and one for
  `acc-naidoo`. A third request path uses no jar at all.
- A `check` helper taking a label, an expected condition and an actual value, printing
  `PASS  <label>  <one-line detail>` or `FAIL  <label>  expected <x>, got <y>`, incrementing a counter,
  and never exiting early. A summary line at the end — `N passed, M failed` — and `exit 1` when `M` is
  non-zero, so the script is usable in a pipeline as well as by eye.
- Every check labelled with its letter, `A` through `H`, in the roadmap's own words as the one-line
  detail, so criterion 1 reads one-to-one against the output.

The eight checks mirror plan 03-13's, over plain `curl`:
- **A** mint a session as `acc-mabaso`; `GET /api/orders` returns exactly two order ids and
  `X-CAP-Account: acc-mabaso`; the same call with `acc-naidoo`'s jar returns a different set; the same
  call with no jar returns 401; `GET /api/orders/wo-0137` under `acc-mabaso`'s jar returns the
  not-found body.
- **B** post a verify-purpose capture on `m-ap003` under `wo-0142` and assert the response header
  `X-CAP-Verification: authored` and a non-zero `X-CAP-Proposals`. Keep the `client_id` you generated
  for this post in a shell variable — it is the `capture_client_id` check D must send — and pull the
  first proposal's `id` and `observation_id` out of the response body with `grep`/`sed` into two more
  variables. Comment why both are needed: AD-5's proposal id is a bare HMAC digest, so the server
  re-derives it from the session's account plus those two fields, and a decision omitting either is
  refused `unknown_proposal`.
- **C** post the same capture with `asset_id: m-gs001` and assert HTTP 409 and
  `"error":"asset_not_in_order"`.
- **D** accept the proposal B kept, sending `"proposal_id"`, `"capture_client_id"` and
  `"observation_id"` from B's variables alongside `"decided_by":"acc-vanwyk"` in the body; assert the
  response contains `"decided_by":"acc-mabaso"` and does not contain `acc-vanwyk`. Comment beside the
  check that a 404 `unknown_proposal` here means one of the two identity fields did not survive the
  shell quoting rather than that the server is wrong, so a reviewer reads the failure correctly.
- **E** `GET /api/walk/wo-0142` and assert the rejected proposal is in `rejected`, `"ran":false` is
  present and `X-CAP-Redaction: none` is on the response.
- **F** post a sync batch twice and assert `X-CAP-Sync-Recorded: 1` then `X-CAP-Sync-Duplicate: 1`; post
  the same `client_id` with a changed field and assert `already_recorded_differently`.
- **G** open `wo-0151`, sleep, `GET /api/hours` and assert a non-zero `elapsed_s`; `POST /api/hours` and
  assert HTTP 405 **and** that the response carries `cache-control: no-store`, `x-cap-store` and
  `x-cap-instance` — that last part is the whole reason the 405 is hand-written.
- **H** read `X-CAP-Instance` from three calls and assert all three match; print the value and a line
  telling the reviewer to re-run after a redeploy and compare, since a platform cold start cannot be
  forced from a shell.

Apply D-10 to every body. Retire the seed's `"sha256":"00","bytes":1` entirely. Use a real 64-lowercase-hex
