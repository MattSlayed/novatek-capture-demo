Perform no `git push` and no merge yourself. Pushing `dev` to produce a Preview deployment is the
developer's git workflow. Present the numbered steps in `<how-to-verify>` verbatim and stop.

When the developer reports the Preview URL and pastes the suite's output, do four things:

1. Read the pasted output against `scripts/curl-suite.sh`'s own labels. Every letter A through H must
   appear exactly once. A missing letter means the script exited early or the paste is partial — ask for
   the rest rather than recording an incomplete run.

2. Fetch the header set yourself for the record, so it is observed rather than transcribed: run
   `curl -s -D - -o /dev/null <preview-url>/api/health` and
   `curl -s -D - -o /dev/null <preview-url>/api/orders/wo-9999` and capture both header blocks verbatim.
   These two are the evidence for Pitfall 3 and Assumptions Log A2.

3. Compare the observed header names against `scripts/server/route-assertions.mjs`'s
   `HEADER_EXCLUSIONS`. For each header the platform sent that is neither one of ours nor already
   excluded, decide and record: is it per-response or platform-added, and therefore an exclusion with a
   reason, or is it something the byte-identity comparison should hold? If an exclusion must be added,
   add it in this same commit with its one-line reason and a comment naming this recorded run as the
   evidence, then re-run `npm run verify` and confirm it is still green. If nothing needs to change,
   record that too — a confirmed list is a result.

4. Create `docs/analysis/server-seam-verification.md` in `deployment-gate.md`'s voice, with these
   sections: `## What was run` (the exact command, the date, the Preview URL and the build id read from
   `NEXT_PUBLIC_BUILD_ID` or the `X-CAP-Instance` value as appropriate — say which); `## Result`
   (the pasted per-check output in a fenced block, unedited, plus the summary line);
   `## Headers the platform added` (both captured header blocks in fenced blocks, and the
   reconciliation decision from step 3); `## What this run does not prove` (that it is one deployment at
   one moment, that a cold start was not forced, and that Fluid Compute concurrency — Assumptions Log
   A1 — is still unmeasured); and a bare `---` plus `Recorded <date>.` as the last line.

   Then append one line to `docs/analysis/single-writer-non-bypassability.md`'s `## What a reviewer can
   run` section pointing at this new document, and strike or amend whichever `## Open items` entries
   this run actually closed. Leave the ones it did not.

If any lettered check reported `FAIL`, do not close the phase. Record the failure verbatim in
`## Result`, open it as a defect in the plan summary, and say plainly which requirement it belongs to.
A red letter here is the suite working, not the suite being wrong.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a local `next start` → a real Vercel deployment | The two do not add the same headers; everything the automated suite proves is proved under the local set only |
| an assumption carried → an assumption tested | Research logged four live-deployment-only facts; carrying them forward unmeasured is how a preview becomes a claim it cannot support |
| a reviewer's shell → the deployment | If the Preview is behind Vercel Authentication, the suite meets a login page and every check fails for the wrong reason |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-3-78 | Repudiation | a phase closed on a local suite alone | mitigate | This plan is non-autonomous and blocking; the phase does not close until a person has run the eight checks against a deployment and pasted the output, and a `FAIL` line is recorded as a defect rather than smoothed over (D-09b). |
