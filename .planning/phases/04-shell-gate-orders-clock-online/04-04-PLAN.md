<objective>
Build the one client projection: the single module that holds every piece of cached server
state for the life of one document, with one purge, keyed on the store instance the server
states on every response.

Purpose: SC-5 requires that all cached server state live in one client projection module with
a single purge operation at the gate, and D-04 requires the projection to purge whenever
`X-CAP-Instance` changes — a projection outliving the instance it was read from is the one
failure the single purge exists to prevent. Module scope is the right lifetime: it survives
every client-side screen switch and resets only on a full document load, which is the same
event that tears down the tab.

Output: one module and its unit test. No library, no Context, no new dependency — the
projection's whole surface is read, write, purge and an instance comparison.
</objective>

                               + X-CAP-Account, X-CAP-Orders               | 401

                               + X-CAP-Order, X-CAP-Account                | 404 { error: "order_not_found", detail }

                               copied value early, and no clock segment is touched)

X-CAP-Instance (lib/http/contract.ts HEADER_TABLE). Every error body is { error, detail }.

re-validate its UUID shape; a missing body returns 400 bad_request, not a clock.

    Add the seven read and write accessors. Each one issues exactly one `fetch` against a
    same-origin `/api/...` path, passes the response through `noteResponse` **before** touching
    the body, then stores what it read and returns it.

    `readSession` reads `GET /api/session` and returns the account or null on a 401 — never
    inspecting, decoding or caching the credential itself, with a comment recording that the
    cookie is `HttpOnly` and unreadable from script, so "is there a session?" is this request
    and nothing else. `endSession` sends `DELETE /api/session`, which clears the credential
    unconditionally; it does **not** purge, because C-29 places the cache purge at the next gate
    entry and because the ended account's queued items and clock segments are deliberately
    untouched by clearing a credential. `readOrders` reads `GET /api/orders` once for both the order list and its
    clocks, storing each order and each clock entry. `readOrder` reads `GET /api/orders/[id]`
    and, on a refusal, returns the envelope's `error` code and `detail` sentence and caches
    nothing. `readHours` reads `GET /api/hours` and replaces every clock entry it carries.

    `openClock` and `closeClock` POST to the two clock routes with
    `content-type: application/json` and a body whose only key is `client_id`, generated with
    `crypto.randomUUID()` **fresh on every call** — record in the comment that reusing one makes
    the second tap a `duplicate` rather than the idempotent success FR-7 describes, and that
    `crypto.randomUUID` is a secure-context API, which is fine on `https` and `localhost` and
    absent on a plain-http LAN origin used for on-device testing. Both store the returned clock
    as the new entry, so no follow-up read is needed, and both return the envelope's code and
    detail on a refusal.

    Every accessor stores the clock entry's arrival as a `performance.now()` reading, not a
    wall-clock instant, and uses `anchorFrom` from `./clock.ts` rather than computing an elapsed
    figure here. Store no derived elapsed figure anywhere: it is rendered arithmetic, not a
    value this module holds (FR-10).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the client → the six frozen route handlers | The only channel. `fetch` over the same origin; no other transport, no server import. |
| `X-CAP-Instance` → the projection | The server's own statement of which store answered. The client compares and purges; it never decides freshness itself. |
| one account's document → the next account's document | The gate's `purge()` is the boundary. Anything cached outside this module would cross it unpurged. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-03 | Information Disclosure | the three `Map`s and `account` | mitigate | One `purge()` with no parameters clears every cell; nothing else in the module resets state, so no partial reset can drift from it. The gate calls it on persona choice. Plan 04-06's sweep asserts no cached server state lives outside this module. |
| T-04-04 | Integrity | `noteResponse` | mitigate | `X-CAP-Instance` is read and compared **before** the body is stored, on every response including a 404, and the header is universal on this seam. A stale projection cannot present a dead instance's records as current. |
| T-04-05 | Tampering | the clock accessors | mitigate | No elapsed figure is stored or sent; the routes accept exactly `client_id` and re-validate its shape, and `POST /api/hours` is 405. A client-derived hour figure is structurally unable to enter the record. |
| T-04-11 | Spoofing | the session credential | mitigate | The client never inspects, decodes or caches the credential. `readSession` is the only authority on whether a session exists; the cookie is `HttpOnly` and verified empty from script. |
| T-04-02 | Information Disclosure | `readOrder`'s refusal path | mitigate | The accessor returns the server's own code and sentence and never branches on *why* the fetch failed, so the client cannot become an existence oracle for what AD-4 defeats on the wire. |
| T-04-07 | Tampering | this plan's commit | mitigate | Two new files; neither is the `[SECURITY]`-blocked pair. The executor commits only the files in `files_modified`. |
| T-04-SC | Tampering | npm installs | mitigate | Zero packages. A state-management or data-fetching library here would be a deviation from CONTEXT.md's Claude's-Discretion note and from D-DEP; `check-named-packages.mjs` is the gate. |
